About the name

ParentNest was designed and built under the internal project name MindNest. The private codebase, its architecture decision records, and its internal documentation use that name; the product, the live demo, and this page use ParentNest. It is the same system and the same engineering record, and this note is the only place the two names need to meet.

The problem

New parents have urgent, specific questions at 3 a.m. and a low tolerance for generic or wrong answers. A conversational AI coach for this audience has to be grounded in vetted developmental content rather than model memory, has to protect unusually sensitive data (children's ages and development, parent mental-health check-ins), and has to behave safely in its wording: no alarming or diagnostic language about a child's development, ever.

The product

ParentNest pairs parents with Nest, a conversational AI coach, inside a complete subscription product: daily age-adaptive developmental activities, a milestone tracker, parent wellness check-ins, a moderated community, multi-child and twins support, age-appropriate product recommendations, and an admin console. Three plans (monthly, annual, lifetime) sit behind a free tier with a daily message allowance of 10. Feature status, stated plainly:

My contributions

I designed and built the system end to end as the sole engineer: the full-stack architecture, the Postgres schema and its security model, the retrieval pipeline and prompt-context assembly, the Stripe billing integration, the test and evaluation harnesses, the CI pipeline, and the documentation set, including five Architecture Decision Records that record the reasoning and trade-offs behind the major choices.

Architecture

System overview: one Next.js application on Vercel, backed by Supabase (Auth, Postgres with Row Level Security and pgvector, one moderation Edge Function), three AI services, and Stripe. Rendered from the project's architecture documentation.

One Next.js 14 (App Router) TypeScript application, strict mode on, deployed on Vercel, serving the UI and 32 server-side API route handlers from a single deployable unit. Supabase provides Auth, Postgres with Row Level Security, Storage, and the Edge Function. The codebase is roughly 13,800 lines of TypeScript/TSX and 1,400 lines of SQL across 22 schema migrations. On each Nest request, middleware refreshes the session and gates the route; the handler resolves the user, checks the free-tier limit against subscription state, retrieves grounding passages by vector similarity, assembles a deterministic per-user context block, and only then calls the model.

Engineering decisions

Decision 1: authorization lives in the database (ADR-0002)

Because the data is sensitive, per-user isolation is enforced by Postgres Row Level Security rather than by application code alone: 37 RLS policies across every user-facing table, with the browser holding only an anon key that can touch the signed-in user's own rows. The reasoning, recorded in the ADR, is that a bug in an API route cannot trivially leak another family's data when the database itself refuses the rows.

Decision 2: answers are grounded, and retrieved text is untrusted (ADR-0003)

The coach's guidance is grounded in a curated knowledge base embedded with Voyage voyage-3 (1024 dimensions) and stored in pgvector inside the same Postgres, so there is no separate vector database to operate and retrieval inherits the same auth and RLS model. Retrieved passages are injected as grounding context and are explicitly treated as untrusted input: the system prompt never executes instructions embedded in retrieved content. That is a deliberate prompt-injection boundary, not an oversight.

Decision 3: billing state has exactly one writer (ADR-0005)

Subscription state decides who gets Premium, so a client must never be able to grant it to itself. Stripe is the source of truth; the webhook handler is the only code path that mutates subscription state. It verifies every event against the webhook secret before writing, and it writes with the server-only service_role key while RLS forbids client writes to the subscriptions table entirely. Entitlements cannot be forged from the browser.

A fourth decision worth naming: one pinned model, claude-haiku-4-5-20251001, at every AI call site (ADR-0004), chosen for predictable latency and unit economics on a free tier, with the ID written explicitly in code so a change is a deliberate, greppable event.

Testing and reliability

Quality is gated in CI on every push, in two jobs. The first runs install, ESLint, TypeScript type-checking, the unit tests, and a production build; the second runs a gitleaks secret scan. The unit suite is 37 tests across the four riskiest areas: context assembly, auth middleware, subscription-status logic, and utilities. More unusual is the deterministic eval harness: before any text reaches the model, the app assembles a per-user context block that encodes product safety rules, and the harness executes the real assembly code against cases that assert those invariants. Expecting parents are never addressed as "mama" and never routed into born-baby logic; dads and partners are addressed by first name; missing data is surfaced honestly instead of fabricated; flagged milestones are framed gently and never with the words "delayed", "behind", or "problem". A failing case fails the build. The harness is deliberately honest about its limits: it checks deterministic code, and does not pretend to score the model's generated replies.

Demonstrated results

Everything here can be checked without an account or any access from me. The live product's landing page is public and reachable anonymously today, under the ParentNest brand. The current source commit passes the full CI pipeline described above, including the secret scan, and the baseline commit before it passed as well. The engineering artifacts are concrete and countable: 5 ADRs, 22 migrations, 37 RLS policies, 32 API route handlers, 37 unit tests, and a deterministic eval harness gating merges. No user counts, revenue figures, or performance numbers are cited: the demo landing page carries marketing language, and marketing copy is not engineering evidence.

Lessons learned

  • For AI products, the testable surface is not only the model: the deterministic layers around it (context assembly, retrieval, entitlement logic) are where safety and correctness can actually be guaranteed, so that is where the tests belong.
  • Security models are cheapest when they are structural: RLS and a single-writer billing path removed whole categories of bugs instead of adding review burden.
  • A pinned, explicit model ID looks like a small thing until you price a free tier: predictability of cost and tone is a feature, and drift is a bug.
